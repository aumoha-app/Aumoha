# Aumoha repository audit — 1 November 2026

**Repository:** `aumoha-app/Aumoha` (private). **Baseline:** `d1b13e6d45c8257502d0e85971bff02f34b58ca7`, branch `main`.

**Conclusion:** The baseline has critical authentication and authorization defects. This branch repairs the verified issues listed below, but outstanding release blockers mean it should not be treated as production approval. No production deployment, database migration, credential rotation, real payment, customer email, or live consultation was performed.

## Scope and evidence

Retrieved the complete recursive repository inventory and all 94 text files, including backend routes/models/middleware, frontend pages/components/auth/payment utilities, PWA worker, configuration, README and scratch scripts. Image filenames were checked against static references in the actual GitHub tree; no missing literal image paths were found. Binary image appearance and git history were not exhaustively audited. Main application persistence is **MongoDB/Mongoose**, authentication is **Firebase**, and video calls use **Agora**; the separate Supabase onboarding forms are outside this repository.

Reviewed route registration and sensitive data paths, traced checkout to booking and call authorization, installed dependencies, built both applications, ran lint and dependency audits, and added isolated HTTP/payment regression tests. Tests mock Firebase verification, database model methods, Razorpay and email services; they exercise the real Express middleware/routes and the real checkout helper without contacting production services. They do not prove MongoDB transaction/index behavior, payment settlement, email delivery or two-device video performance.

## Remaining release blockers and follow-up work

These are confirmed code/design gaps unless explicitly labelled unverified. They are not represented as fixed by this branch.

| Priority | Area and source | Required work |
|---|---|---|
| P1 | `index.ts` instant-match locks | Replace the process-local Set and two-minute timer with a MongoDB-backed atomic reservation owned by the requesting UID. Require reservation ownership at creation, check busy state atomically and prevent requests from releasing another user's lock. Current creation can bypass `/find`; multi-server safety is not established. |
| P1 | Scheduled/reschedule/cancel slots (`index.ts`, `appointmentUtils.ts`) | Store absolute appointment instants/timezone and concrete occurrence IDs. `Today`, `Tomorrow`, `Daily`, month/day parsing and server/browser local time can drift or permanently consume recurring slots. Rescheduling still needs atomic claim/release and rollback; preserving booked slots during provider replacement must be enforced. |
| P1 | Booking/payment lifecycle | Add a persisted payment status and server-owned checkout intent tied to service/provider/slot/price; define Pay Later eligibility. The current UI explicitly offers Pay Later and records appointments as confirmed. This branch preserves that behavior rather than deciding business policy. Payment capture can precede slot allocation; conflict/failure recovery requires an idempotent webhook, refund/retry workflow and reconciliation queue. |
| P1 | Cancellation/rejection/refunds | Current routes can mark a paid booking cancelled/rejected without issuing a Razorpay refund. Add explicit refund state and approved cancellation policy; prevent invalid/repeated state transitions and accidental reopening/releasing of later reservations. The exact-slot release fix is not a full lifecycle state machine. |
| P1 | Donation persistence and payment reuse | Add a durable donation ledger with unique payment IDs, purpose-bound order intents and idempotent receipt issuance. A valid captured payment can currently be reused for multiple donation receipts or for different purposes. The captured-payment check alone does not resolve this. |
| P1 | Community privacy (`/api/users`, `/api/users/rescuers`, SOS/activity feeds) | Signed-in users can enumerate phone numbers, addresses and participant contact fields. Define directory opt-in, consent and field visibility; return reduced public projections and reveal contacts only to permitted participants. Add pagination and rate limits. |
| P1 | Rescue operations (`SupportRequestDetail.tsx`, SOS backend) | Persist responder acceptance, assignment, acknowledgement and resolution instead of relying on WhatsApp links or treating clicks as rescues. Verify actual emergency contacts and map positions operationally. The backend does not establish an automatic dispatch/notification service. |
| P1 | Data migration and configuration | Reconcile existing duplicate payment/order IDs before the new unique indexes; inspect and remove previously seeded demo/approved provider records through a deliberate migration. Configure and verify real provider registrations; model defaults currently contain sample qualification/registration/rating values. No live database was inspected or changed. |
| P2 | Agora calls | Verify two real devices, camera denial, audio-only behavior, reconnects, token renewal after one hour and teardown. Token fetching no longer silently bypasses auth, but the UI still needs a clear recoverable error screen. The in-memory signaling buffer needs expiry, limits and a shared service for multi-instance deployment. |
| P2 | Account erasure | Profile deletion leaves the Firebase account, appointments, SOS posts, activities, media and email-provider data. Define retention and implement a deliberate end-to-end erasure/anonymization flow. |
| P2 | Email and uploads | Escape user input in HTML emails; use a durable outbox with retries and delivery status. Existing callers often ignore `sendEmail=false`. Validate file MIME/size, protect medical documents with authorized access and avoid broad base64 payload storage. |
| P2 | Input/platform protection | Add route schemas, per-user/IP throttling, structured errors, request tracing and secure headers. CORS alone does not authorize requests. Verify production API URL/CORS, Firebase authorized domains, secrets, backups, health/readiness and monitoring. No production settings were inspected. |
| P2 | Marketplace/cart | Checkout is a WhatsApp enquiry, with no durable order, inventory, shipping, payment or seller fulfillment workflow. Cart clears immediately after opening WhatsApp, even if no order is sent. Keep product claims and stock aligned with actual sellers. |
| P2 | UI/data quality | Remove remaining UI sample doctors/ratings/metrics and simulated location/distance values; distinguish actual verification from community roles. Admin pending-provider UI, responsive interactions, keyboard/screen-reader access and all loading/error/empty states need browser QA. API data is not the only source of demo content. |
| P2 | Dependencies/lint | Remaining moderate audit findings and lint warnings need scoped cleanup; avoid npm audit's proposed major downgrades without compatibility review. There were no existing checked-in tests/CI workflow in the reviewed inventory. This branch adds tests; wire them into your preferred CI. |

## Before merging or deploying

1. Review this draft and the outstanding P1 items. Do not deploy solely because builds pass.
2. Rotate the previously committed Razorpay test secret and any shared admin passcodes; check provider dashboards/history for other exposures. Values are intentionally not repeated in this report.
3. Set `ADMIN_EMAILS` to the actual verified admin addresses or provision signed Firebase custom admin claims. A database-only `role: admin` is intentionally insufficient. Configure `ADMIN_PASSWORD` for the existing second-lock UI.
4. Configure Razorpay keys, auto-capture or the capture workflow, Firebase identity verification, MongoDB and Agora app certificate on staging. Existing orders without server `app_user_uid` notes cannot pass the new payment check; reconcile them before rollout.
5. Check duplicate nonempty `razorpayPaymentId` and `razorpayOrderId` values, back up the collection, then explicitly verify successful unique-index creation before enabling paid bookings. This audit did not run the migration.
6. Test signup verification, verified login, admin/provider access, scheduled Pay Later and paid bookings, payment/slot conflicts, instant acceptance/rejection, cancellation/refund, prescription access, rescue submission, email delivery and two-device video with staging data. Confirm the new failure states communicate clearly to users.
7. Email/password users now need verified email ownership; signup/signin sends a verification link. Existing unverified accounts must complete verification. The updated worker clears its previous caches and no longer supplies cached private pages offline.
8. Use Node 24 (the audited runtime) and the committed lockfiles with `npm ci --prefix backend` and `npm ci --prefix frontend`; run both test suites, backend build, frontend build and lint. Confirm SMTP compatibility after the Nodemailer major upgrade and live provider behavior after dependency changes.
